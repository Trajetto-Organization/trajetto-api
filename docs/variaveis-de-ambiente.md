## Onde cada valor mora

| Ambiente                          | Onde                                                                                                                                                                              | Observação                                                                                                                                                        |
| --------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Desenvolvimento                   | `.env` na raiz (copiado de `.env.example`)                                                                                                                                        | o **único** arquivo que a API lê; `.env.development`, `.env.staging`, `.env.production` e `.env.test` não são carregados por nada e não são versionados           |
| Staging e produção: API           | aba _Environment_ da Application **`trajetto-api`**, no projeto `trajetto-api` do environment `staging` ou `production` do Dokploy                                                | seções 1 a 12 deste documento; uma variável por linha, `NOME=valor`, sem aspas                                                                                    |
| Staging e produção: IA            | aba _Environment_ da Application **`trajetto-ai`**                                                                                                                                | seção 9 (`AI_TOKEN`, `OCR_THREADS`, `AI_MAX_QUEUE`)                                                                                                               |
| Staging e produção: migrations    | aba _Environment_ da Application **`trajetto-api-migrate`**                                                                                                                       | seção 2: só a `DATABASE_URL` sem tetos de runtime (e, numa instalação nova, o bootstrap e o usuário master, uma vez)                                              |
| Staging e produção: backup        | o dump: nenhuma variável, aba _Backups_ do Database PostgreSQL no Dokploy. O PITR e a memória do banco: aba _Environment_ do **Database PostgreSQL** (imagem `trajetto-postgres`) | seção 14; a API não lê nenhuma delas                                                                                                                              |
| Produção: cópia fora da conta     | aba _Environment_ da Application **`trajetto-offsite`** (só na produção)                                                                                                          | seção 14: as `OFFSITE_*`, lidas pelo `infra/r2/offsite-copy.sh`                                                                                                   |
| Staging e produção: banco e Redis | campos dos Databases **PostgreSQL** e **Redis** do Dokploy (usuário, senha, banco, imagem, comando)                                                                               | não são variáveis de ambiente que você digita; a seção 13 diz quais campos e onde cada valor reaparece. No PostgreSQL, _Command_ e _Args_ ficam vazios (seção 14) |
| CI (validação)                    | bloco `env:` dos workflows                                                                                                                                                        | valores fixos de teste, sem segredo (banco e Redis dos service containers)                                                                                        |
| CI (deploy)                       | _environments_ `staging` e `production` do GitHub e variáveis do repositório                                                                                                      | seção 16                                                                                                                                                          |

Salvar o _Environment_ de uma Application não reinicia nada: a mudança vale
no próximo **Deploy** (do painel ou do pipeline).

O app mobile não lê nada daqui (a URL da API dele vem dos environments do EAS,
`trajetto-mobile/docs/variaveis-de-ambiente.md`); a web lê as dela no
Environment da Application da web (`trajetto-ui/docs/variaveis-de-ambiente.md`)
e divide com a API só `RATE_LIMIT_FORWARDER_SECRET` e `TURNSTILE_SECRET_KEY`.
As quatro `MAP_TILE_*` (o mapa de fundo, [seção 11](#11-documentação-app-webhooks-e-auditoria))
não são compartilhadas, mas levam os **mesmos valores** nas duas: a web as
lê para os mapas dela, e a API as entrega ao app.
A tabela completa do que precisa casar entre a API, a web e o app (URLs,
origens, segredos compartilhados, R2, IA, push) é a mesma nos três
repositórios: [`deploy.md` → Os três repositórios juntos](./deploy.md#26-os-três-repositórios-juntos).

## Como a API lê o ambiente

- `src/env/index.ts` carrega o `.env` (com `dotenv-expand`: `${VAR}` dentro
  do arquivo funciona) e valida com o schema zod
  `src/schemas/env-schema/index.ts`. Valor faltando ou inválido derruba o
  boot com `Invalid enviroment variables` e a lista do que corrigir.
- Em staging e produção não há `.env`: o contêiner recebe exatamente as
  variáveis do _Environment_ da Application `trajetto-api`. Toda variável que
  a API lê pode ser definida lá; a que não estiver lá não existe (vale o
  padrão). `${VAR}` **não** é expandido no Environment do Dokploy: escreva os
  valores por extenso (por exemplo, a `DATABASE_URL` inteira).
- **Vazio conta como ausente** (`defined-env.ts`): `NOME=` vale o mesmo que
  não ter a linha, e o padrão dela continua valendo.
- Travas de produção (`NODE_ENV=production`, que a imagem sempre é):
  `UPLOAD_STORAGE_TYPE=r2` com as quatro `R2_*`; `RATE_LIMIT_TRUSTED_PROXY`
  definida; servidores públicos do OpenStreetMap recusados; `https` no mapa e
  no geocoder. Em staging **e** produção (`APP_ENV`): `JWT_SECRET` e
  `JWT_SECRET_REFRESH_TOKEN` com 32+ caracteres, diferentes entre si e sem o
  prefixo `GENERATE_`.
- Mapa de fundo do app (`MAP_TILE_URL`, `MAP_TILE_URL_DARK`), em qualquer
  ambiente: modelo inválido derruba o boot (https com `{z}`, `{x}` e `{y}`;
  http só com `APP_ENV` de desenvolvimento), e fora de desenvolvimento
  `tile.openstreetmap.org` é recusado. A mensagem cita o nome, nunca o valor.
  "Inválido" inclui o que a web aceita e o app recusa, porque a página do
  mapa do app só deixa entrar imagens de **uma** origem (o CSP precisa
  nomeá-la): host curinga (`*`), `{s}` sozinho no host ou direto sobre o
  domínio de topo (`https://{s}.com/…`), `{s}` no meio de um nível ou outra
  vaga no host (`{r}`), credenciais (`usuário:senha@`), IPv6, `_` no host,
  ponto no fim do host, espaço, aspas, `<`, `>`, `\`, crase ou `*` em
  qualquer lugar, e mais de 1024 caracteres. Servido, um modelo assim faria
  o app mostrar "Mapa de fundo não configurado" com a variável definida. Os
  modelos reais da web passam: o do MapTiler (com ou sem `{r}`) e
  `https://{s}.tile.provedor.com/…`.
- `DATABASE_URL` não está no schema: quem a lê é o Prisma (e os scripts de
  boot). Sem ela o boot para ao esperar o Postgres.

## Como gerar os segredos

| Segredo                                                                                                                                      | Comando                                                          |
| -------------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------- |
| `JWT_SECRET`, `JWT_SECRET_REFRESH_TOKEN`                                                                                                     | `openssl rand -base64 48` (duas vezes: valores diferentes)       |
| senha do Redis, token da IA (`AI_LOCAL_TOKEN` = `AI_TOKEN`), `RATE_LIMIT_FORWARDER_SECRET`, `RATE_LIMIT_EDGE_SECRET`, `ROLLOUT_STATUS_TOKEN` | `openssl rand -hex 32`                                           |
| senha do Postgres                                                                                                                            | `openssl rand -hex 24` (hex: entra na `DATABASE_URL` sem escape) |
| `WEBHOOK_SECRETS_KEY`                                                                                                                        | `openssl rand -base64 32` (exatamente 32 bytes)                  |
| `MASTER_USER_INITIAL_PASSWORD`, `DOCS_PASSWORD` (20+)                                                                                        | `openssl rand -base64 24` (ou o gerenciador de senhas)           |
| chave SSH do CI (só com `ROLLOUT_VERIFY=ssh`)                                                                                                | `ssh-keygen -t ed25519 -f <nome> -N ''`                          |

Nenhum segredo vai para o repositório, para o log nem para um print. Segredos
**diferentes** em staging e produção.

## Legenda

- **Obrig.**: `sempre` (o boot falha sem ela em qualquer ambiente), `prod`
  (o boot falha sem ela com `NODE_ENV=production`), `deploy` (o boot não
  exige, mas sem ela o ambiente fica errado — defina em staging e produção),
  `não`.
- **Segredo**: 🔒 = trate como senha (Dokploy, gerenciador de senhas; nunca em
  log); vazio = não é segredo.
- **Dev / Staging / Produção**: o valor esperado em cada ambiente; "—" = não
  definir. Salvo indicação, staging e produção ficam no _Environment_ da
  Application `trajetto-api`.

## 2. Banco de dados

O banco de staging e o de produção são Databases **PostgreSQL** do Dokploy
(seção 13). Há duas URLs que **você monta** com os dados do Database
(usuário, senha, banco e o _Internal Host_, que é o App Name): a de runtime,
na `DATABASE_URL` da Application `trajetto-api`, e a **sem tetos de
runtime**, na `DATABASE_URL` da Application `trajetto-api-migrate` (a etapa
de release: `prisma migrate deploy` e os seeds;
[`deploy.md` → 15](./deploy.md#15-migrations)). O modelo abaixo chama a
segunda de `MIGRATION_DATABASE_URL`, o nome que ela teve na API. Os
parâmetros depois do `?` são fixos — copie inteiros:

```
DATABASE_URL=postgresql://<USUÁRIO>:<SENHA>@<APP NAME DO POSTGRES>:5432/<BANCO>?schema=public&connection_limit=10&pool_timeout=5&connect_timeout=5&socket_timeout=60&max_idle_connection_lifetime=300&options=-c%20statement_timeout%3D30000%20-c%20lock_timeout%3D5000%20-c%20idle_in_transaction_session_timeout%3D60000
MIGRATION_DATABASE_URL=postgresql://<USUÁRIO>:<SENHA>@<APP NAME DO POSTGRES>:5432/<BANCO>?schema=public&connection_limit=2&connect_timeout=10
```

Exemplo de host: `trajetto-postgres-production` (staging:
`trajetto-postgres-staging`). O porquê de cada parâmetro, e no que cada um vira
no pool do `pg` (Prisma 7 com `@prisma/adapter-pg`), está em
[`arquitetura.md`](./arquitetura.md#conexão-com-o-postgres).

**O usuário de cada URL** (plano de escala, X-15). Até o corte dos roles, o
`<USUÁRIO>` de todas é o do Database, superusuário e dono das tabelas.
Depois, cada URL do runtime usa o login do seu papel, criado pela etapa de
release (`infra/sql/20-runtime-roles.sql`) e liberado à mão pelo dono; o
passo a passo e a conta das conexões estão em
[`deploy.md` → roles do banco](./deploy.md#roles-do-banco-logins-urls-e-conexões).

## 14. Backup do banco

São dois, lado a lado:

- **O dump diário do Dokploy** não tem variável. Desde 26/10/2026 ele é o
  _Backup_ do próprio Database PostgreSQL no Dokploy (aba _Backups_),
  configurado no painel: um _S3 Destination_ do Cloudflare R2 (_Settings →
  S3 Destinations_, com o token R2 só do bucket de backup), agenda diária e
  retenção de 30 cópias. O passo a passo está em
  [`deploy.md`](./deploy.md#18-backup-e-restauração). O antigo serviço
  `trajetto-backup` e as variáveis dele (`PG*`, `BACKUP_R2_*`,
  `BACKUP_AGE_RECIPIENT`, `BACKUP_HEARTBEAT_URL`, `BACKUP_AT_UTC`,
  `BACKUP_RUN_NOW`) não existem mais (tabela no fim deste documento).
- **O PITR (pgBackRest) e a memória do banco** vêm da imagem
  `trajetto-postgres` do Database (plano de escala, onda 3) e leem as
  variáveis abaixo, digitadas à mão na aba _Environment_ do **Database
  PostgreSQL** de cada ambiente, não na `trajetto-api`. A ordem de ligar,
  os valores de cada ambiente e os Schedule Jobs estão em
  [`deploy.md`, seção 27](./deploy.md#27-pitr-com-pgbackrest).

Vazio conta como ausente. Nenhum valor inválido impede o banco de subir: o
wrapper da imagem (`infra/postgres/trajetto-entrypoint.sh`) volta ao padrão
e avisa no log. Os scripts trocam qualquer chave, senha ou URL de check por
`<redacted>` na saída e nos pings. _Command_ e _Args_ do Database ficam
vazios: eles passam por cima do wrapper.
